## 官方方案中需要保留的区别

官方提供带 `Signed-By` 的 APT 仓库配置，可以用包管理器安装和维护 sing-box。
这不等于自动满足本项目的账号、服务权限、配置和升级验证要求。
[官方安装文档](https://sing-box.sagernet.org/installation/package-manager/)

核对 1.14.0 发布源码后，需要同时考虑以下内容：

| 内容 | 官方发布配置 | 对本项目的影响 |
| --- | --- | --- |
| 服务 | `sing-box` 用户；包含网络管理、原始套接字等多项 capability；从 `/etc/sing-box` 目录加载配置 | 保留目前单文件配置和仅绑定低端口的能力，不能直接换用完整默认 unit |
| 默认配置 | 固定示例密钥，TCP 8080 | 使用本项目首次随机生成、重复执行保留的密钥和 TCP 443 |

## 第一批：主机初始化

新增独立 Bash 入口 `scripts/harden-vps.sh`（`prepare` / `apply` 必须分开调用），保留原安装器只负责代理安装的职责。
输入限于管理员名、公钥文件路径和明确的现有 SSH 端口；SSH 私钥留在 Mac。
单台主机使用普通备份、清楚的阶段报错和人工恢复说明，不引入通用状态机。

1. **准备管理员**：验证公钥、创建账号、锁定本地密码、设置 authorized_keys 权限；
   用 `visudo` 检查明确选择的 `ALL=(ALL:ALL) NOPASSWD: ALL` 完整管理员提权权限。
   此步保留旧 SSH 登录方式。目标管理员已存在且无法确认兼容、同名配置或公钥冲突时停止；不拒绝无关的预置普通账号。
2. **操作者建立新连接**：保持旧会话和控制台可用，在 Mac 以指定密钥、已确认 host key、
   `en4` 和禁用连接复用的新 SSH 会话验证登录及 sudo。VPS 本机 `su` 不能代替外部登录验证。
3. **收紧与验证**：只在前一步成功后，从新管理员会话明确执行收紧步骤。
   输入端口同时核对实际监听、有效配置及活跃的 ssh.socket，不符时在防火墙修改前退出。
   备份并检查 sshd 语法及管理员/root 的有效配置，关闭 root、密码和键盘交互认证，保留端口。
   核查完整原生防火墙，先添加已核对的 SSH 放行，再启用双栈入站/转发拒绝、出站允许和 TCP 443；拒绝覆盖未知规则。
   配置每日安全更新和禁止自动整机重启。首次及后续每天都允许必要服务重启和短暂中断；首次操作安排在允许中断的窗口。
4. **再建连接并验收**：验证新管理员、禁止认证方式、sudo、UFW 和 SS2022 HTTPS；之后才关闭旧会话。
   重启由操作者另行明确安排，核验启动后的同组结果。

首批自动化仅承诺已经在一次性 Ubuntu 24.04 VM 验证的路径。
至少覆盖成功、重复执行、错误公钥、未知防火墙、SSH 候选检查失败、操作中断后可用入口与备份恢复。
不把操作者一句“已登录”当成自动采集的新连接证据；人工检查与测试采集分别记录。

## 第二批：私密取回与导入

拟新增小型 Mac Bash 入口 `scripts/fetch-vps-config.sh`，接收目标 IPv4、SSH 端口、管理员、
本机身份文件路径、已确认的主机密钥记录、物理网卡及输出路径。接口细节随实现和合成测试定稿。

通过固定身份检查的 SSH 和 `sudo -n` 读取服务端配置；数据直接进入当前用户的私密临时文件，
不分配远程 TTY、不回显正文、不经 argv/环境变量或日志传递密钥。
读取失败、SSH 返回非零、JSON/算法/密钥格式错误时，不发布目标文件。
成功时以 0600 保存，**任何已有输出都拒绝覆盖，发布操作本身必须具有排他性**。
输出目录的所有权和权限必须保证其他用户不能替换目录项；临时文件与目标在同一文件系统。
不能用“先检查不存在、再普通 rename”代替排他发布；补测发布前另一个进程创建目标的竞争，原文件必须不变且脚本失败。
服务端配置保持 root:sing-box 0640，不为 SFTP 放宽权限，也不把管理员加入服务账号组。

先兼容已有 `connect-vps.sh setup` 的服务端 JSON 输入，不另造订阅或配置分发协议。
地址显式传给 setup，导入后验证真实 HTTPS 并增加 Cloudflare 出口与指定 VPS IPv4 的比较。
检查传输中断、host-key 不符、链接目标、已有文件、非法配置和敏感数据不出现在日志的失败场景。
当前后台 TUN 的候选生成和切换继续使用明确的维护步骤，私密下载成功不能自动触发后台替换。

## 第三批：程序升级流程

先交付单次、明确版本的维护流程：审查官方发布说明与制品摘要，保留旧程序和配置，
用候选版本检查真实配置，再安排替换与服务重启，验证 PID、端口、稳定运行和 Mac HTTPS。
失败时恢复这次保存的旧版本/配置并重新验证。代理密钥保持不变，不能把普通安装器重跑当成升级入口。
Mac 固定版本后台和 VPS 分别检查；Homebrew 简易客户端与当前固定目录后台仍是不同的维护路径。

APT 迁移先在 VM 做独立实验，闭合下列四项后再决定是否采用：

- 官方仓库签名信任、明确版本选择，以及升级时的包文件/安装脚本变化。
- 包默认配置、服务账号与 `/usr/bin`、`/usr/local/bin` 两个安装位置的明确交接。
- 最小权限 unit 和不需要的 Polkit/D-Bus 授权在安装、升级、回退全过程中的处理。
- 配置检查、旧包可恢复性、服务重启时机和链路失败后的实际恢复。

Ubuntu 目前的自动安全更新仅允许 Ubuntu security 来源；不会因为以后添加 SagerNet 源就自动维护 sing-box。
如果 APT 迁移需要的持续适配明显超过收益，继续维护固定官方程序也符合这个单机项目的目标。

## 完整部署的组合门槛

第二批完成后，在同一台干净 VM 依次运行管理员 prepare、新 SSH 登录、apply、现有 prepare-vps.sh、
私密取回、客户端导入及 HTTPS 出口检查；随后重复执行并核对原密钥、账号、组和规则，
最后受控重启，再验证新 SSH 与代理。第一批只独立验收主机初始化；这条组合测试通过后才可宣称完整部署可复现。
